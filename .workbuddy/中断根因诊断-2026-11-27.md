## 二、为什么压缩这么频繁却永远压不下去（真正的 bug）

### 证据 1：token 分母是 unknown，90% 阈值形同虚设

```
tokenCount=204605/unknown (?%, threshold=90.0%), force=true
```

995 次压缩日志里，**分母全是 `unknown`**，百分比算不出来（`?%`）。阈值 90% 永远无法判定，于是每次都走 `force=true` 的紧急压缩分支。

### 证据 2：压缩后 tokenCount 不降反升

连续 20 次压缩的 tokenCount：

```
210275 → 208905 → 212647 → 216819 → 218415 → 219360 → 221825
→ 219404 → 227073 → 229858 → 229327 → 232325 → 217626
→ 219037 → 221115 → 221441 → 204605
```

**全程在 204K~232K 之间震荡，一次都没掉下去。**

### 证据 3：historyLen 只增不减，压缩裁的是「视图」不是「计数」

```
23:31:31  tc=221825  historyLen=1971
23:32:43  tc=227073  historyLen=2020
23:33:51  tc=229327  historyLen=2069
23:34:49  tc=232325  historyLen=2095
23:39:02  tc=221441  historyLen=2155
```

同期 `Smart boundary trim done: 2020 items → 27 kept`——**裁到只剩 27 条，但 historyLen 下一轮照样涨到 2155，tokenCount 照样 221K。**

说明 trim 只影响「这一轮发给模型的切片」，下一轮又从全量历史重建视图。**压缩是个空转的循环。**

### 证据 4：连续压缩撞上限被强制熔断

```
23:34:49 [Compact:MaxToken] consecutiveMaxTokenCompactCount=5/5
23:35:37 [Compact:MaxToken] LIMIT REACHED: 5 >= max=5, stopping compact loop
```

撞到 5/5 上限后停止压缩 → 但 token 还是 217K → 用户一发消息又触发 → 再撞 → 再停。**这就是「几分钟压了 4 次」的机制。**

## 三、token 为什么恒在 200K+：固定开销吃满了

压缩裁历史无效，说明大头不在历史条目里，而在**每轮都重新注入的固定部分**：

| 来源 | 实测数据 |
|---|---|
| 技能列表注入 | 系统提示原文 `Showing 200 of 507 skills` —— **507 个技能**，每条含名称+描述+路径 |
| MCP 服务器 | `mcp.json` 配了 **14 个**，其中 `github` 单个暴露 **46 个工具** |
| AGENTS.md | 11,983 字节，每轮必进 |
| 内置工具定义 | 本会话工具表约 118 KB |
| 项目记忆 | 工作记忆 + 用户记忆 + 画像结论，每轮注入 |

仅「507 个技能 + 14 个 MCP 工具表」两项，粗估就在 100K~150K tokens 量级。**压缩把历史从 2000 条裁到 27 条省下的那点，被这块固定开销直接抹平。**

## 六、账号被登出（独立问题，与中断非同一根因）

- `deleteAccountSnapshotSync` = 账号快照被删，是登出的执行动作。
- 会话切换后 `auth:login` 卡 38~64 秒，最终 `saveAccountSnapshotSync` 重新登录。
- `wb:notifications:summary` 401 从 UTC 03:32 起每 30 秒一次，累计 1219 次；重登后恢复。
- **401 是症状不是根因**；`/health` 的 `canRefresh=false`、`tokenExpiresAt=null` 才是线索。
- 已排除：自动更新（`~/.agent2api/updates/` 无新包，`installedUpdateVersion` 仍是 3.5.0-beta.1）。

## 七、结论：一句话

> **不是网断了，也不是模型挂了。是「上下文压缩」在空转：token 分母 unknown 导致 90% 阈值失效、每次强制压缩、压缩只裁视图不裁计数、token 恒在 200K+；而 200K+ 的底座是 507 个技能 + 14 个 MCP + 每轮固定注入，不是历史。压不动 → 撞 5/5 上限 → 掐掉正在跑的请求 → 表现为「停」。**

## 八、止血方案（按见效速度排序）

### 立刻（用户操作，0 风险）

1. **新开一个会话**。当前 `da6b6f40` 历史已 34.7 MB / 3093 行，压缩已证明救不回来。
2. **重启 WorkBuddy 客户端**。释放 renderer 的 2.5 GB，复位 `sdk/conversations/*.log` 的 EPERM 内部状态，清掉 14 小时累积。

### 短期（改配置，显著降底座）

3. **砍技能数量**：507 → 只留常用 30~50 个。把 `~/.workbuddy/skills/` 下不用的目录移走（`alice/_modules` 下 424 个是最大来源）。
4. **砍 MCP**：14 个 → 常用的 3~5 个。`github` 单服务器 46 工具，不用时先停。
5. **清缓存**：`logs` 2.3G + `traces` 1.8G + 废弃会话 1.26G，可回收约 5 GB。

### 中期（要改客户端，非本项目）

6. `tokenCount` 的分母 `unknown` 必须修——没有 contextWindow 就无法算百分比，`threshold=90%` 是死配置。
7. `Smart boundary trim` 必须真正回写到 `historyLen` / `tokenCount`，否则永远是空转。
8. 压缩不应以 `Aborting session` 掐断在途请求；应排队等当前 turn 结束再压。
