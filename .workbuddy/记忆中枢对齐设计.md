## 0. 对齐口径：功能对齐，代码重写

AgentHub 记忆中枢文件头写着「禁止在未经本人授权的情况下直接搬运本代码」。所以：

| 允许 | 禁止 |
|---|---|
| 照它的**功能规格 / 数据结构 / 交互流程**重写 | 复制 `.cjs` 源码、逐行翻译 |
| 沿用同一套 frontmatter 键名、目录约定（**跨端互操作必需**） | 把它的 Vue 组件搬成 Rust/JSX |
| 沿用同一套 MCP 工具名与语义（客户端无感切换） | 引入它的 Electron/node:sqlite 依赖 |

跨端互操作的价值很高：同一份 `~/.agent2api/memory/` 可以被 AgentHub 直接读、被 WebDAV 同步到另一台机器。所以**磁盘格式（frontmatter + 路径）按 AgentHub 抄齐**，实现自己写。

## 2. 磁盘格式（跨端互操作契约）

### 2.1 目录布局

```text
{config_dir}/memory/
  config.json                    模块配置（分组见 §3）
  projects.json                  项目 registry（slug → 名称/远程/本地路径/别名/来源）
  device.json                    设备 id（同步冲突判定用）
  index.db                       派生索引（可删，重建即还原）
  profile-cache.json             画像镜像（本地 profile/*.md 丢了能自愈）
  runtime/                       调度器运行态、报告、导出临时
  general/
    l1/<agent>/<YYYY-MM-DD>.md   ← 全局日常，一天一文件多节
    l2/decisions/<id>.md
    l2/knowledge/<id>.md
    l2/insight/<id>.md
    l2/summary/<id>.md
  projects/<slug>/
    l1/<agent>/<YYYY-MM-DD>.md
    l2/{decisions,knowledge,insight,summary}/<id>.md
  profile/
    persona.md  preferences.md  tech.md  habits.md
    .history/<ts>-<name>.md      每次重生成前的旧版
  trash/<id>.md                  回收站（保留 N 天后彻底删）
```

**与现状的兼容**：现有 `projects/<slug>/<id>.md` 与 `projects/_global/<id>.md` 继续被 `load_all()` 扫描（`legacy` 标记），
首次 `rebuild` 时**不自动搬迁**（避免大规模重写用户文件）；新写入一律走新布局。旧条目在索引里照常可读可编辑。

## 4. 检索打分（七项混排）

AgentHub 默认权重与 agent2api 现状对照：

| 项 | 含义 | AgentHub 默认 | agent2api 现状 |
|---|---|---|---|
| `bm25` | 相关度（FTS5 负分取反） | 0.50 | 1.0（未归一） |
| `recency` | 时间衰减 `exp(-Δ/半衰期)` | 0.15 | 布尔「7 天内 +1」 |
| `importance` | 静态重要度 | 0.10 | `×2.0` |
| `affinity` | 同项目/同 Agent 加成 | 0.15 | 无（只做过滤） |
| `graph` | 图扩散（`mem_link` 一跳） | 0.05 | 无 |
| `heat` | 使用热度 `log(1+access)` | 0.10 | 无 |
| `layer` | l2 优先于 l1 | 0.05 | 无 |
| 置顶/星标 | 硬加成 | `+3 / +1`（未归一） | `+3 / +1` |

对齐后：`score = Σ(w_i × norm(x_i)) + 3·pinned + 1·starred`，`norm` 全部压到 0..1 再乘权重 —— 现状的「bm25 原始分 + 常数」在库大了之后会被 bm25 单项主导，这是要修的真缺陷。

**图扩散**：`mem_link(src,dst,kind)` 三种边 —— `supersedes` / `same_project` / `tag_shared`。查询命中后按 `search.graphExpansionDepth`（默认 1）跳、最多补 `graphExpansionMax`（默认 5）条。

## 6. 待确认队列（review_queue）

三种 kind：

| kind | 触发 | 推荐动作 | 自动裁决 |
|---|---|---|---|
| `supersede` | 失效判定任务 / 写入时 `supersedes` 低置信 | 标旧条目失效 | **永不自动**（会让真结论变假） |
| `classify` | 项目模糊匹配（score ∈ [阈值, 1)） | 归入候选 slug | 置信 ≥ 0.95 且 slug 已登记 → 自动搬 |
| `dedup` | L2 判定「疑似重复」 | 留信息量大的那条，另一条标取代 | 精确重复（score 1.0）或 ≥ 0.9 → 自动合并 |
| `distill` / `consolidate` | 蒸馏 / 合并任务 | 新增一条 l2 | 默认自动（只新增、幂等，删掉即回原样） |

**判据**：`review.autoResolve`（默认开）+ `review.autoResolveFloor`（默认 0.85，低于它一律留人）
+ 各类型自己的开关与阈值（见 `config.rs`）。自动落地时 `review_queue.resolution` 写
`auto-<kind>`，与人工的 `manual` 分得开；日志里有「自动裁决 …（置信 x）」一行。

**永不物理删除** —— 去重只标 `superseded_by`，归类只是搬文件，两者都能倒着走回去。

> 2026-11-24 从「默认全关、全部等人点头」改成「按类型分档、高置信自动落地」：
> 真机 62 条 pending（classify 17 / dedup 45）躺了多日无人处理，而实际用法是
> 「全选 → 确定」。闸门没筛掉任何东西，只把每条建议推迟一个月后被 `review_expire`
> 静默作废。四类建议的写操作全部可逆，可逆的写操作不该当闸门，该当审计日志。

## 8. 内部 LLM 通道（#41 的关键设计）

**不新写供应商客户端。** 复用网关自己：

```text
memory::llm::complete(task, prompt)
  → 选模型：models.routing[task] 按标签过滤 → 命中则用；否则用 config 的默认模型
  → 取一个可用网关 Key（api_keys::list() 里 is_usable 的第一条；无则登记「未配置」并挂起任务）
  → POST http://127.0.0.1:{port}/v1/chat/completions   （Bearer 该 Key）
  → 落 llm_call{task, provider, model, tokens_in/out, ok, latency_ms}
```

理由（与 `tool_services::vision` 完全同构，直接照抄那条已验证的路）：

1. 协议转换、重试、故障转移、限流、请求日志、计费口径**全都不用重写**；
2. 用户改模型池 / 加了新供应商，记忆任务自动跟着变；
3. 不额外持有上游凭证 —— 只持一个本机网关 Key，泄漏面不变。

**无 Key / 无模型时**：任务返回 `Skipped("未配置模型")`，队列不推进（不丢数据、不阻塞主流程），页面提示「去工具服务配一个模型」。

### 13.2 与设计稿的偏差（都是有意为之）

1. **`ready` 与列表截断分开**
   设计里干跑只要求「会导入多少条」。实现里额外区分 `ready`（真会写入的条数，
   不受 `limit` 影响）与 `listed`（列表里实际列出多少）。原因是早先拿
   `importable.len()` 当 `ready`，页面会出现「说 60 条、实际写 800 条」。

2. **干跑记录放内存，不落盘**
   设计稿没规定。实现用进程内 `AtomicI64`。`preview` 对外承诺「一个字都不写」，
   往 `index.db` 塞时间戳会让这句话变成假的；进程重启后失效是特性。

3. **导入走 `BatchWriter` 而不是逐条 `write`**
   `write` 的精确去重要 `store::load_all()` 全盘读。单条没问题，批量导入是
   O(n²)。`BatchWriter` 在构造时把现存 l1 的 hash 收成集合，之后每条只查集合。
   语义不变（同一份 hash 判重规则），只是把「每条约一次全盘读」换成「整批一次」。

4. **`import.sources` 用竖线分隔的裸字符串**
   设计稿写的是对象数组。`Kind::List` 只接受字符串数组，改校验层只为了「更好看」
   不划算。格式：`路径|格式|启用|优先级`。

5. **导入来源支持 `~/` 展开**
   设计稿没提。页面示例写的是 `~/.claude/projects`，而 `PathBuf::from` 不认 `~`，
   不展开的话用户照着填只会看到「路径不存在」。

6. **单个来源单次最多 800 个文件**
   设计稿没设上限。`~/.claude/projects` 攒一年能上万，全导进去既拖慢检索也让
   第一次导入无法收尾。超出的下次再导，hash 去重保证不重复。页面同时显示
   `files`（真实总数）与 `take`（本次会读的数量）。

7. **导入页 `view()` 不读正文**
   只列文件、数个数。读正文是这条链路最贵的一步（一次会话记录可能几 MB），
   为了数个数把每个文件解析一遍，等于打开页面就跑一次全量干跑。

8. **没有做「最近 7 天热力图」**
   设计稿仪表盘里写了。当前没有按天聚合的接口，做一个假的分块图不如不做。

### 13.4 已知的更早实现坑（修完留档）

这几个不是设计偏差，是**写错了**，修完后留在这里避免重犯：

1. **配置路径自己依赖自己**：`store::config_file()` 曾写成 `root().join(...)`，
   而 `root()` 要读 `storage.root` 配置 —— 首尾成环，主线程首次读配置即崩。
   配置文件位置必须是不依赖配置的常量路径。
2. **slug 丢了 owner/repo 边界**：先拼 `owner--repo` 再整体过 `sanitize_slug`，
   连续分隔符被压成一个，`aimod-cc--agent2api` → `aimod-cc-agent2api`，
   两个不同项目会算成同一个。必须逐段合法化后用 `--` 连接。
3. **会话记录信封没解开**：`collect_text` 不挖 `message` 键，Claude Code 的
   `{type,message:{role,content:[...]}}` 一条都读不出来，且**静默**表现为导入 0 条。
